# BWE-OCA-ARTICLE

> **Where it runs (local or cloud):** `Z:\Backup\websites\OneClickAnswers` below is the owner's local Windows checkout and is optional. In any other checkout (a cloud Claude Code project, Linux or macOS) use the repository root, the folder that holds `CLAUDE.md`; nothing in this skill needs the `Z:` drive. See docs/CLAUDE-PROJECT-MIGRATION.md.
>
> **Cloud sessions:** step 9 does not apply. Do not deploy; say NOT deployed (cloud session) and hand the work over through a pull request (see docs/WORKFLOW.md "Local and cloud sessions").

Usage: `/BWE-OCA-ARTICLE "<the question>"`. Project: `Z:\Backup\websites\OneClickAnswers`. Read `docs/BLOG_ARTICLES.md` first (files, states, writing rules, quality gate). The blog is for ordinary people and their everyday questions. It is not documentation or a developer blog. Stop and ask the owner at any step that needs a decision.

Workflow:
1. **Is the question worth it?** Would an ordinary person click it because the question itself is interesting, and can we give a useful or surprising answer? If not, say so and stop. Having an OCA tool is a bonus, never a requirement.
2. **Duplicate and cannibalization check.** Search the registry (`src/registry/articles.ts`), the posts (`src/blog/posts.ts`, `posts-more.ts`, `articles.ts`), the Answer Engine (`src/answers/content.ts`, e.g. `/what-is/apr`), tool pages and category pages for the same intent. If one exists, recommend UPDATE EXISTING, MERGE, a SUPPORTING article or DO NOT BUILD, and wait for the owner.
3. **Find the tools.** Tool Registry ids from `src/registry/*.ts`. Only real ids; never force an unrelated tool. Reuse an existing engine for any interactive element (`src/lib/article-try.ts`); never write a second formula.
4. **Research and verify.** Use authoritative primary sources (U.S. government, standards bodies, universities, original manufacturers). Fetch and READ them (WebFetch/WebSearch); never cite a page you did not read, never cite another calculator site, never fabricate a citation. Where a page could not be fetched, say so in the registry `researchNote`. Note the date checked for anything that changes. Do not invent history or repeat popular myths: if sources disagree, say so.
5. **Work out every number independently** (Python, a definition) before writing; the test must not call the code it checks.
6. **Write the post** in `src/blog/articles.ts`: slug, title (65 characters or fewer), h1, description (80 to 165), `status: 'draft'`, `series`, `question`, `tools`, `related` (2 or more existing slugs), `method` and/or `sources` (plain text, no links), `disclaimer` where the subject needs one (money, food safety, health, legal; types in `src/lib/disclaimer.ts`). Body: an `answer` block FIRST (shown as "The Simple Answer"), then plain explanation, a worked example, the interesting part, optional `table`/`fact`/`try`, and `tool` blocks. Rules: plain words (grade 6 to 8), short paragraphs, no filler, no em dashes, no clichés ("in today's fast-paced world", "whether you're a", "it's important to note", "let's dive in"...), no outbound links, no fake authors or "reviewed by", no invented statistics.
7. **Add or update the registry entry** in `src/registry/articles.ts` with the `o(title, area, cluster, tools, S(usefulness, interest, toolRelevance, originalValue, evergreen, monetization, linkingValue, difficulty), { draft: true, why, note })` helper: the eight scores are judgement from 1 to 5 (difficulty = how hard to make authoritative), every search field stays null and the evidence stays `SEO data not verified`, `draft: true` sets `status: 'draft'` and `researchStatus: 'sources-verified'` ONLY when real sources were read, `why` says why it is in the first batch, `note` says what was and was not verified (say so when a page could not be fetched). A blocked idea (HIGH-risk money, a review still open, no reliable source) is not drafted: give it `hold` or `high` and its reason.
7b. **Set the post's `area`, `care` (money, food-safety, health, legal) where the subject needs it, `lastReviewed` and `related` (two or more existing slugs).** Run the quality gate: `npx tsx` a small script with `checkArticle` from `src/lib/article-quality.ts` or just `npx vitest run tests/blog-articles.test.ts`, which runs it on every draft. A failing check blocks the article; the checks a person must judge stay manual.
8. **Tests** in `tests/blog-articles.test.ts`: hand-worked numbers, the notice, the sources. Run `npx vitest run tests/blog-articles.test.ts tests/pages.test.ts tests/site.test.ts`, `npm run registry:export`, `npm run check`, then the full `npx vitest run`.
9. **Stage.** `npm run deploy:staging` (unless `.deploy-disabled` exists: then say NOT deployed). Show `https://staging.oneclickanswers.com/blog/<slug>`. Check it on a phone width.
10. **Report** per the work-reporting rules in `docs/WORKFLOW.md`: question, answer, sources actually read, tools linked, related articles, notice type, tests, and what was NOT verified.

Hard rules: **never** set `status: 'published'`, edit `publication.ts`, run `npm run deploy -- --confirm` or release; production needs the owner's explicit approval and `/BWE-OCA-CHECKPOINT`. Do not edit the shared BWE-SEO engine. Never write a search volume, keyword difficulty, CPC or traffic number.
